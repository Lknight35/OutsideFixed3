# Outside architecture and engineering boundaries

## Decision and scope

The preserved Vite/React prototype is a visual reference. Its single large component, browser capture, generated place activity and local state cannot enforce account or privacy boundaries. The additive `mobile/` native application and `server/` service replace those subsystems without deleting the prototype. Expo/React Native gives iOS and Android a shared component system, native camera/GPS, secure token storage and native map integrations. Shipping binaries still requires native build/signing workflows; a browser preview does not validate device camera behavior.

The implemented backend is one Node 22 process using Express 5, SQLite WAL, disk media storage, FFmpeg and a trusted moderation CLI. This is a working local development service, with no paid dependencies or invented content. SQLite's constraints and explicit transactions keep invitation recipients, upload consumption and contribution credit consistent. Database/API ownership belongs to Astra; Sol owns native screens against [the API contract](api.md). Critical authorization stays in `server/src/domain.js`, not in UI visibility checks. Backend tests use isolated databases and clearly identified test fixtures; runtime never seeds videos or accounts.

## Data and trust boundaries

- Accounts use asynchronously computed scrypt password hashes with individual random salts. Sessions are 256-bit opaque tokens, hashed at rest and expiring after 30 days. Logout revokes the server record. Only the account owner can read or change preferences. Email is accepted for exact friend search but never returned in public profile shapes.
- Profile photos accept only actual JPEG/PNG/WebP still images, at most 5 MiB and 16 megapixels. Sharp decodes, normalizes orientation, crops to 256×256 JPEG and strips metadata before private disk storage. Reads require an authenticated account; replacement/deletion removes the old file. Gallery image selection for a profile photo is separate from, and does not enable, camera-roll video contribution.
- Account deletion requires password reauthentication and an explicit native confirmation. It revokes every session, removes personal media, profile images, preferences, saves, recorded locations, friendships and affected chats. Shared invitation records remain with a non-loginable “Deleted account” tombstone, stripped organizer notes, and no accessible chat. Pending file erasures are durably queued and retried on startup/hourly if the filesystem operation fails; all API access is revoked immediately. An active upload/transcode must finish before deletion to avoid racing media writes. Original email can be registered again as a new, unrelated account. Email verification and password recovery remain unconfigured.
- Friendship is one unique unordered pair with an explicit pending/accepted/declined state. Only the invited recipient accepts it. Friend maps require both mutual friendship and the owner's map-sharing preference.
- A hidden place suppresses its owner's association across maps, recent places, feed, saved videos, direct video and media APIs, and activity notifications. The public geographic place still exists independently in search. Hidden places never appear as redacted markers or counts. Unhiding restores eligible visibility. `private` videos are owner-only. Access is checked for every media request, including HTTP range playback.
- Invitations are organizer-owned records with individual recipients. Organizer reads include all private responses; each recipient reads only their own response. A chat is keyed by invitation plus recipient, never a group. Every message read/write checks membership, acceptance and server time. Visible chat expires exactly at outing end + 24 hours; invitation details remain. Routine chat data is physically purged after an additional 30 days. This is a documented local retention default, not a complete legal-hold system.
- Save records are user-owned and filtered through current authorization on every read. Notification preferences are enforced when generating inbox entries. Friend activity notifications are also reauthorized when read. The inbox works locally; OS push delivery is not configured. No continuous location collection exists.

## Recording, processing and moderation

A capture ticket binds an authenticated account, a server-resolved OpenStreetMap place, server issue time, and fresh GPS evidence. Fixes must be within 30 seconds, ≤100 metres reported accuracy, and ≤250 metres from the selected place. An explicitly mocked location is rejected. The ticket expires in ten minutes and is atomically consumed once. The native UI exclusively exposes rear-camera capture and no gallery import. Upload uses a fresh post-capture location fix checked against HTTP arrival time so slow transfer does not invalidate freshness.

These are location checks, not cryptographic proof of native capture. An altered client can lie about GPS, camera direction or source media. `recordedAt` is server ticket issuance, not camera hardware attestation; duration is checked against the available capture window. Strong device attestation, signed capture challenges and fraud analysis are required before stronger authenticity claims. The public API deliberately calls the evidence `location_checked`.

Multipart uploads are capped at 40 MiB, one clip, bounded fields. MIME checks are followed by actual FFprobe container/stream inspection; both FFprobe and FFmpeg restrict demuxers to MOV/MP4 and Matroska/WebM, rejecting disguised playlists that could reference other local files. Clips must be 2–60 seconds, up to 4K, with one video stream. FFmpeg reads local files only, uses a bounded process timeout and two threads, strips metadata and outputs 720px H.264/AAC MP4 with fast-start plus a JPEG thumbnail. The serial queue bounds transcoding concurrency. Inputs remain private; nothing is anonymously served. An upload whose HTTP response is lost can be retried with the same ticket to retrieve the same video.

Database states are `processing → pending → approved/rejected`, with `failed → processing` retry. Restart resumes `processing` jobs; failed input remains available for recovery. Operator review is mandatory before discovery and reward credit. Reporting creates a real moderation queue. Use `npm run moderate -- list`, inspect the private local processed file, then `approve <id>` or `reject <id> <reason>` from a trusted shell. There is no app-facing approval endpoint or embedded administrator credential. This provides an operational review path; it is not automated harmful-content detection or a staffed trust-and-safety service.

Approved recordings expire from public discovery after seven days. Owners keep their memories, and authorized friends can access shared map memories after discovery expiry. Hiding a location or removing friendship revokes access immediately. Rejected content is unavailable to everyone except its owner and trusted operator.

Three approved quality contributions unlock 30 days of advanced-feature entitlement. Credit is limited to one contribution per user/place/UTC capture day, and exact duplicate files cannot earn credit twice across approved uploads. The server alone increments credit, extends the grant, and revokes advanced access when moderation reduces the earned batch count. This is an entitlement system; advanced AI recommendation products remain unimplemented and are never advertised as working. No subscription or payment integration exists.

## Places and evidence

Search uses genuine Nominatim results with stable `osm:<type>:<id>` identifiers and OpenStreetMap attribution. Explicit submitted searches are cached for 24 hours, globally serialized at ≤1 request/second and bounded per account. There is no autocomplete against the public Nominatim service. Nearby results are genuine previously indexed places ordered by haversine distance; they are not a comprehensive nearby-business catalogue. Search errors remain errors, with no invented fallback records. Place coordinates describe the provider's geometry centre, which can be unsuitable for very large parks/venues; users should select the specific venue or entrance they can actually verify near.

The feed returns only approved, unexpired, authorized footage. Categories come from place metadata; optional interests select genuine recordings and optional proximity limits to 50 km. An optional text query matches all meaningful whole words in actual captions and place metadata after authorization; it ignores obvious query fillers and never infers activity or atmosphere. For example, “quiet coffee” only matches an approved update whose caption/place data contains both words. Search results remain timestamped evidence, not a claim that the described activity is still happening. There are no fabricated crowd levels, scheduled events, vibes, predictions, likes, follower counts or popularity ranking. Semantic questions such as “hip-hop tonight” cannot currently be answered without matching evidence; this milestone supports real place lookup and conservative text search of actual recorded updates.

## Production evolution and release constraints

Keep a modular monolith. Before public launch, move relational data to PostgreSQL/PostGIS and media to private S3-compatible storage with short-lived authorized delivery. Introduce a durable processing queue and HLS renditions when load/device measurements justify them. Preserve the same authorization policies through these migrations. Replace the public Nominatim service with a production provider or operated index before significant traffic. Add authenticated moderation UI, stronger fraud controls, account verification/recovery, blocks/abuse controls, durable distributed rate limits, secure OS push, audited backups and restore tests, metrics/alerts, and privacy retention tooling.

TLS, a stable reachable API hostname, deployment and store signing are not configured by this local build. The client API URL must match a device-reachable server; device loopback is the device itself. Local HTTP is development only. `CORS_ORIGINS` permits explicit browser development origins; native clients do not rely on CORS as authorization. Never expose the development process or SQLite/media directory directly to the public Internet. The system needs integration tests on actual iOS and Android hardware for camera, permissions, GPS, connectivity recovery and secure storage before release.

## Local operations

Requires Node 22.13–22.x, FFmpeg and FFprobe on PATH. In `server/`, run `npm ci`, `npm test`, then `npm start`. `GET /healthz` checks SQLite and returns server time. Default bind is `0.0.0.0:8787`; override `HOST` and `PORT`. `DATA_DIR` defaults to `server/data` when started from that directory and contains SQLite/WAL plus uploads and processed files; keep it private, persistent and excluded from Git. Optional `FFMPEG_PATH`, `FFPROBE_PATH`, `CORS_ORIGINS`, and identifying `OSM_USER_AGENT` configure the service. The supplied cloud Node lives at `/workspace/.outsidefixed3/node-v22.23.5-linux-x64/bin`.

Logs contain event names and opaque IDs, not credentials, email, coordinates, or private message bodies. Backups must include SQLite and media consistently; no automated backup job is claimed. The standard start command resumes queued media, and process shutdown waits for active processing. Startup, domain/security tests, real provider lookup and real FFmpeg processing must be verified separately; see the task's validation report for executed outcomes.
